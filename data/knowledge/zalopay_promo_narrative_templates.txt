PROMO DECISION TREE:
IF %abuse weekly > 2-3%:
  → Identify top campaign by totalAbuse
  → Check if campaign was recently launched or modified by business team
  → Check if campaign is split into sub-campaignIDs → aggregate manually
  → IF Coin2DD involved: check SME earn path (FIRST_SCANQR, CHECK_CASHLOAN tasks)
  → Deploy challenge/reject on top abuser cluster

IF %abuse weekly < 1% (unusually low):
  → DO NOT report as improvement
  → Check FAD model status (production deployment, score distribution)
  → Check BAD_V2 cluster sizes (are they dropping below ≥5 threshold?)
  → Check impact table: if Reject + Challenge also declining → confirm visibility loss
  → Add manual review layer to validate true abuse level

IF Coin2DD rate > 5%:
  → Check SME merchant involvement in earn side
  → Check Coin2DD appID and user overlap with known abusers
  → IF > 7%: escalate, likely SME contributing → apply SME-specific controls

IF detection drop pattern (FAD + BAD_V2 both declining):
  → Root cause analysis: model refresh? campaign structure change? rule timeout?
  → Temporary: reactivate manual monitoring / legacy rules as safety net
  → Medium term: BAD_V2 threshold adjustment (≥5 → ≥4); DS capacity for FAD fix
